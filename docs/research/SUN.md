# Visible sun and corona rendering

## Source contract

Pinned gta-reversed [TimeCycle.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/TimeCycle.cpp) calculates the visible sun angle as minutes today times pi/720. Its native Z-up vector is `(0.7 + sin(angle), -0.7, 0.2 - cos(angle))`, normalized. The browser's placement rotation maps this to `(nativeX, nativeZ, -nativeY)`. This is not the same as the source's separately initialized directional-light vector; that initialization also has platform annotations. Do not use the visible orbit as proof of native directional illumination or shadow orientation.

[Coronas.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Coronas.cpp) registers the sun only when the current area can see outside. The core is eligible when native elevation is greater than -0.1, and the corona when it is greater than zero. Their colors come from separate timecycle channels. Both are placed at camera position plus the normalized sun vector times 95% of far clip. Stored sun size is multiplied by 2.7335 for the core and 6 for the corona. The core has no flare or LOS check; the corona uses a sun flare and an LOS check. Both use the shiny-star corona texture. Registration is only the first stage: actual visibility, intensity and size depend on the later update and rendering paths.

The inspected renderer uses additive ONE/ONE blending and disables depth writes. Its textured branch projects a position pulled 1.5 units toward the camera, scales the vertical extent by fogginess and reduces RGB correspondingly. It also writes depth-test state inside that branch, so the registration LOS flag alone is not a complete description of draw-time depth behavior. Corona intensity fades, obstruction checks, lens flares, sprite projection and render-state ordering require their own verification.

## Current browser implementation

`world/sun.ts` supplies the normalized path in browser coordinates and the two registration elevation thresholds. `WorldLighting` uses these for the visible sky core and halo, independently of the existing authored directional light/shadow path. Local timecycle input now supplies separate core and corona RGB, using the same explicit sRGB-to-linear presentation mapping as sky endpoints. Clearing the input restores authored colors. The path applies with or without a local table; it is a clock rule rather than weather-table data.

The sky still draws a procedural disc and a power-function halo with fixed angular extents. Their additive contribution is evaluated inside the sky shader before output conversion. This does not reproduce the native textured sprite shape, stored size, screen projection, additive display-space behavior, fade history, weather scaling, LOS, lens flare or indoor rules. Applying the source's size multipliers to this unrelated disc formula would falsely suggest compatible units, so those values are documented rather than routed to arbitrary shader thresholds. Original retail visual comparison and trigonometric/float precision remain unverified.

## Sprite metrics and fade foundation

Further inspection of pinned [Sprite.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Sprite.cpp) establishes the `CalcScreenCoors` contract. After transforming by the native camera view matrix, it rejects depth less than or equal to near clip plus one, and depth greater than or equal to far clip, when the corresponding checks are enabled. Position scales by viewport width/height divided by depth. The two size scales additionally multiply by `70 / FOV`. This is not sufficient evidence to substitute a normal Three camera-space point: native view-matrix offset/scale conventions must be traced. The called `RenderOneXLUSprite_Rotate_Aspect` implementation is still an original-address trampoline in this source, so its final quad extents are unresolved here.

[RegisteredCorona.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/RegisteredCorona.cpp) resets target alpha to zero when registration is absent. Obstruction/cloud checks and the prior render's offscreen flag can cause fading toward zero. Otherwise intensity approaches target alpha; the camera-look brightness override takes effect only in this unobstructed, onscreen branch. Each update narrows the result to a byte. A newly created zero-intensity slot survives its first update, while an older zero slot is released. Native timestep units derive from milliseconds divided by 20 in [Timer.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Timer.cpp); normal engine clamping happens before corona updates. Do not feed seconds directly into the fade formula or collapse updates into a frame-independent interpolation. Sun corona updates also affect the global light multiplier; that coupling is not implemented by the helper.

`render/corona.ts` now provides native-view sprite metrics, the unattached fade stage and half-range distance attenuation as separate calculations. Callers must supply the resolved obstruction flags, prior offscreen state, native timestep, registration and creation state. It does not perform raycasts, manage slots, update global light intensity, convert Three matrices or issue draws. For supported values it uses JavaScript arithmetic and byte truncation; original float precision remains unverified. Invalid nonfinite inputs and zero-depth division with disabled clipping are explicitly rejected rather than reproducing undefined output.

Verification: 237 unit tests across 47 files and build passed. New cases cover viewport/FOV/depth scaling, exact clipping boundaries and bypass flags, byte truncation across split updates, target saturation, missing registration, obstruction precedence over immediate brightness, initial slot survival and distance attenuation. These are source-transcription checks, not retail executable comparisons. The module is not yet imported by the playable renderer, so browser and production runs were not repeated for this foundation. The previously verified playable sun remains unchanged.

## Browser camera adapter

Pinned gta-reversed [Camera.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Camera.cpp) attaches the game's view matrix to `RwCamera::viewMatrix`; it does not establish an ordinary orthonormal camera-space matrix. Independent RenderWare reimplementation [librw camera.cpp](https://github.com/aap/librw/blob/18532c2e13efbc1aa43f0b00b4459831f9414de0/src/camera.cpp) supplies the projection convention: perspective view coordinates include scale by inverse twice the view window and a half-depth offset. Its comments explicitly distinguish this matrix from the separate view/projection matrices used by OpenGL and D3D. librw is supporting implementation evidence, not original SA executable proof.

`render/coronaProjection.ts` now converts the current Three perspective camera's homogeneous clip position to equivalent top-left screen numerators: `(clipX + clipW)/2`, `(clipW - clipY)/2`, with forward depth `clipW`. The existing native sprite helper then applies viewport scaling, its near-plus-one/far checks, and its size scale. This matches the browser camera's projection, including asymmetric view offsets. The caller updates camera matrices first. The native size-FOV scalar is a separate argument; silently treating Three's vertical FOV as `CDraw::GetFOV()` would claim an unverified equivalence. No horizontal clipping is added because the native helper does not do it.

Verification: 239 unit tests across 48 files, build and the targeted browser projection test passed. Unit cases compare normalized-device-coordinate projection across landscape/portrait viewports, transformed cameras and view offsets; separate cases verify size-only FOV changes and depth-based rejection. The GPU fixture projects six independently rendered red planes through centered/off-axis cameras and reads the corresponding framebuffer pixels. This confirms compatibility with the browser renderer, not native FOV, raster precision or sprite half-extents. The adapter is not yet connected to playable corona draws, so the full gameplay suite and production smoke were not repeated. Texture selection, final quad rules, persistent state, obstruction and native visual comparisons remain unfinished.

## Persistent sun state in play

`SunCoronas` now owns separate core/corona records across playable frames. Registration updates position at 95% of camera far clip and copies current color. When registration ends, the record retains its previous world position and color while fading toward zero; it is released when its intensity expires. The first zero-intensity update preserves a new record. Projection writes the offscreen flag after fading so the following update consumes the previous projection result. Returning the camera to the sun therefore resumes its fade after the expected flag delay. Camera matrices are updated after imported far-clip changes and before projecting either record.

The renderer passes frame duration in seconds; the controller converts to native timestep units and caps at three. Zero duration stays zero for browser frame handling rather than introducing the original timer's minimum positive step. The core and halo now have independent direction and intensity uniforms so one can continue fading at its last registered position after the other's eligibility changes. The current procedural shader maps byte intensity to a fraction of 255; native sprite color/intensity arithmetic and original display blending remain separate work. Obstruction, clouds, outside-area eligibility, immediate camera-look brightness changes and the global light multiplier are not yet connected. This introduces persistent rendering behavior without claiming those missing source stages.

During browser validation, the new duration check exposed a negative main-loop delta after resume: the queued animation-frame timestamp can predate the newly assigned `performance.now()` baseline. The main loop now clamps its duration to the range zero through 0.1 seconds, preventing negative input to rendering and simulation-clock accumulation.

Verification: 243 unit tests across 49 files, all 50 browser tests, build and production smoke passed. State tests verify separate colors, identity reuse, first-frame survival, release after missing registration, prior-projection visibility, offscreen recovery, retained world positions, changed far clips and the timestep cap. The GPU test warms the source-based fade for the existing position/color checks and separately measures initial core pixels of 0, 18 and 36 before reaching 255. These pixels validate the current procedural intensity mapping, not native sprite blending. The full browser run includes the previously failing resume path. Production reported no page errors, external runtime requests or development hook, and its gameplay capture was inspected.

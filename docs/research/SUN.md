# Visible sun and corona rendering

## Source contract

Pinned gta-reversed [TimeCycle.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/TimeCycle.cpp) calculates the visible sun angle as minutes today times pi/720. Its native Z-up vector is `(0.7 + sin(angle), -0.7, 0.2 - cos(angle))`, normalized. The browser's placement rotation maps this to `(nativeX, nativeZ, -nativeY)`. This is not the same as the source's separately initialized directional-light vector; that initialization also has platform annotations. Do not use the visible orbit as proof of native directional illumination or shadow orientation.

[Coronas.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Coronas.cpp) registers the sun only when the current area can see outside. The core is eligible when native elevation is greater than -0.1, and the corona when it is greater than zero. Their colors come from separate timecycle channels. Both are placed at camera position plus the normalized sun vector times 95% of far clip. Stored sun size is multiplied by 2.7335 for the core and 6 for the corona. The core has no flare or LOS check; the corona uses a sun flare and an LOS check. Both use the shiny-star corona texture. Registration is only the first stage: actual visibility, intensity and size depend on the later update and rendering paths.

The inspected renderer uses additive ONE/ONE blending and disables depth writes. Its textured branch projects a position pulled 1.5 units toward the camera, scales the vertical extent by fogginess and reduces RGB correspondingly. It also writes depth-test state inside that branch, so the registration LOS flag alone is not a complete description of draw-time depth behavior. Corona intensity fades, obstruction checks, lens flares, sprite projection and render-state ordering require their own verification.

## Current browser implementation

`world/sun.ts` supplies the normalized path in browser coordinates and the two registration elevation thresholds. `WorldLighting` uses these for the visible sky core and halo, independently of the existing authored directional light/shadow path. Local timecycle input now supplies separate core and corona RGB, using the same explicit sRGB-to-linear presentation mapping as sky endpoints. Clearing the input restores authored colors. The path applies with or without a local table; it is a clock rule rather than weather-table data.

The sky still draws a procedural disc and a power-function halo with fixed angular extents. Their additive contribution is evaluated inside the sky shader before output conversion. This does not reproduce the native textured sprite shape, stored size, screen projection, additive display-space behavior, fade history, weather scaling, LOS, lens flare or indoor rules. Applying the source's size multipliers to this unrelated disc formula would falsely suggest compatible units, so those values are documented rather than routed to arbitrary shader thresholds. Original retail visual comparison and trigonometric/float precision remain unverified.

## Sprite metrics and fade foundation

Further inspection of pinned [Sprite.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Sprite.cpp) establishes the `CalcScreenCoors` contract. After transforming by the native camera view matrix, it rejects depth less than or equal to near clip plus one, and depth greater than or equal to far clip, when the corresponding checks are enabled. Position scales by viewport width/height divided by depth. The two size scales additionally multiply by `70 / FOV`. This is not sufficient evidence to substitute a normal Three camera-space point: native view-matrix offset/scale conventions must be traced. The called `RenderOneXLUSprite_Rotate_Aspect` implementation is still an original-address trampoline in this source, so its final quad extents are unresolved here.

[RegisteredCorona.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/RegisteredCorona.cpp) resets target alpha to zero when registration is absent. Obstruction/cloud checks and the prior render's offscreen flag can cause fading toward zero. Otherwise intensity approaches target alpha; the camera-look brightness override takes effect only in this unobstructed, onscreen branch. Each update narrows the result to a byte. A newly created zero-intensity slot survives its first update, while an older zero slot is released. Native timestep units derive from milliseconds divided by 20 in [Timer.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Timer.cpp); normal engine clamping happens before corona updates. Do not feed seconds directly into the fade formula or collapse updates into a frame-independent interpolation. Sun corona updates also affect the global light multiplier; that coupling is not implemented by the helper.

`render/corona.ts` now provides native-view sprite metrics, the unattached fade stage and half-range distance attenuation as separate calculations. Callers must supply the resolved obstruction flags, prior offscreen state, native timestep, registration and creation state. It does not perform raycasts, manage slots, update global light intensity, convert Three matrices or issue draws. For supported values it uses JavaScript arithmetic and byte truncation; original float precision remains unverified. Invalid nonfinite inputs and zero-depth division with disabled clipping are explicitly rejected rather than reproducing undefined output.

Verification: 237 unit tests across 47 files and build passed. New cases cover viewport/FOV/depth scaling, exact clipping boundaries and bypass flags, byte truncation across split updates, target saturation, missing registration, obstruction precedence over immediate brightness, initial slot survival and distance attenuation. These are source-transcription checks, not retail executable comparisons. The module is not yet imported by the playable renderer, so browser and production runs were not repeated for this foundation. The previously verified playable sun remains unchanged.

## Browser camera adapter

Pinned gta-reversed [Camera.cpp](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Camera.cpp) attaches the game's view matrix to `RwCamera::viewMatrix`; it does not establish an ordinary orthonormal camera-space matrix. Independent RenderWare reimplementation [librw camera.cpp](https://github.com/aap/librw/blob/18532c2e13efbc1aa43f0b00b4459831f9414de0/src/camera.cpp) supplies the projection convention: perspective view coordinates include scale by inverse twice the view window and a half-depth offset. Its comments explicitly distinguish this matrix from the separate view/projection matrices used by OpenGL and D3D. librw is supporting implementation evidence, not original SA executable proof.

`render/coronaProjection.ts` now converts the current Three perspective camera's homogeneous clip position to equivalent top-left screen numerators: `(clipX + clipW)/2`, `(clipW - clipY)/2`, with forward depth `clipW`. The existing native sprite helper then applies viewport scaling, its near-plus-one/far checks, and its size scale. This matches the browser camera's projection, including asymmetric view offsets. The caller updates camera matrices first. The native size-FOV scalar is a separate argument; silently treating Three's vertical FOV as `CDraw::GetFOV()` would claim an unverified equivalence. No horizontal clipping is added because the native helper does not do it.

Verification: 239 unit tests across 48 files, build and the targeted browser projection test passed. Unit cases compare normalized-device-coordinate projection across landscape/portrait viewports, transformed cameras and view offsets; separate cases verify size-only FOV changes and depth-based rejection. The GPU fixture projects six independently rendered red planes through centered/off-axis cameras and reads the corresponding framebuffer pixels. This confirms compatibility with the browser renderer, not native FOV, raster precision or sprite half-extents. The adapter is not yet connected to playable corona draws, so the full gameplay suite and production smoke were not repeated. Texture selection, final quad rules, persistent state, obstruction and native visual comparisons remain unfinished.

## Persistent sun state in play

`SunCoronas` now owns separate core/corona records across playable frames. Registration updates position at 95% of camera far clip and copies current color. When registration ends, the record retains its previous world position and color while fading toward zero; it is released when its intensity expires. The first zero-intensity update preserves a new record. Projection writes the offscreen flag after fading so the following update consumes the previous projection result. Returning the camera to the sun therefore resumes its fade after the expected flag delay. Camera matrices are updated after imported far-clip changes and before projecting either record.

The renderer passes frame duration in seconds; the controller converts to native timestep units and caps at three. Zero duration stays zero for browser frame handling rather than introducing the original timer's minimum positive step. The core and halo now have independent direction and intensity uniforms so one can continue fading at its last registered position after the other's eligibility changes. The current procedural shader maps byte intensity to a fraction of 255; native sprite color/intensity arithmetic and original display blending remain separate work. Obstruction, clouds, outside-area eligibility, immediate camera-look brightness changes and the global light multiplier are not yet connected. This introduces persistent rendering behavior without claiming those missing source stages.

During browser validation, the new duration check exposed a negative main-loop delta after resume: the queued animation-frame timestamp can predate the newly assigned `performance.now()` baseline. The main loop now clamps its duration to the range zero through 0.1 seconds, preventing negative input to rendering and simulation-clock accumulation.

Verification: 243 unit tests across 49 files, all 50 browser tests, build and production smoke passed. State tests verify separate colors, identity reuse, first-frame survival, release after missing registration, prior-projection visibility, offscreen recovery, retained world positions, changed far clips and the timestep cap. The GPU test warms the source-based fade for the existing position/color checks and separately measures initial core pixels of 0, 18 and 36 before reaching 255. These pixels validate the current procedural intensity mapping, not native sprite blending. The full browser run includes the previously failing resume path. Production reported no page errors, external runtime requests or development hook, and its gameplay capture was inspected.

## Camera-look brightness transitions

The pinned `CCoronas::Update` combines left, right and behind flags with a fourth bit when `CCamera::GetLookDirection()` returns zero. A changed mask sets the immediate-brightness counter to three; an unchanged mask decrements it before updating records. Eligible onscreen records use target alpha while that counter is positive. Offscreen/obstruction fading takes precedence. Returning to the original mask is another change and can retrigger the counter. The zero-valued native look direction is an unknown enum state in `Camera.h`, distinct from forward (3) and behind (1); it must not be inferred from a browser mode named “none.”

The playable left/right/rear camera views now provide bits 1/2/4 to `SunCoronas`; ordinary forward view supplies zero. The controller preserves the preceding mask and three-update counter per session. The fourth native bit remains unrepresented by current camera modes, though the controller accepts the full four-bit mask for future integration. The same persistent source-inspired state feeds both procedural sky components. The browser applies this at render-update cadence; original process/pause scheduling, remaining camera modes and retail frame timing are not established by these checks.

Verification: 245 unit tests across 49 files, build, targeted rear-view and sun browser checks, and production smoke passed. Unit cases verify exactly three eligible updates, expiry, retrigger on return, offscreen precedence and release with absent registration. The GPU check measures red-channel progression 0, 18, then 255 when a look-mask change overrides the normal fade. The real control test verifies rear view and release/pause behavior. Production reported no page errors, external runtime requests or development hook. The full browser suite was not repeated for this focused change. Textured sprite rendering, obstruction/cloud inputs, indoor eligibility, global light coupling and retail visual comparison remain unfinished.

## Static collision obstruction

The playable corona now resolves an obstruction callback against the simulation's collision world. The ray runs from the retained corona world position to the camera and ends at the camera, matching the source query's endpoint order. Rapier's fixed-only and exclude-sensors filters omit vehicles, kinematic actors and trigger volumes. Unattached world collision and fixed-body triangle collision remain eligible. The core does not perform this LOS query; the source registers it with obstruction checking disabled. Ordinary rendered surfaces can still cover the procedural core through scene depth.

Obstruction reaches the existing byte fade stage before the camera-look brightness override. A blocked corona fades to zero and expires; renewed clear registration creates and fades in a record. Queries use the retained position even after registration ends. The callback is connected in `GameRenderer` and applies to both authored world collision and imported collision installed into the simulation.

This is a static-collision approximation of `CWorld::GetIsLineOfSightClear` with buildings enabled and vehicles/peds/objects/dummies disabled. Imported fixed objects are not yet classified into the original entity categories, so fixed non-building objects may also block the browser query. Native surface filtering, triangle sidedness/precision, cloud occlusion, indoor eligibility and the original collision engine remain unverified. No claim of exact native LOS behavior follows from the filter names alone.

Their mask-name entries are empty; the sun's shiny-star slot therefore does not request a separate mask raster. The same texture is used for the core and corona registration. This lookup contract is distinct from selecting an arbitrary visible texture from a particle dictionary.

`decodeNamedTextures` now exposes the existing model texture resolver to non-model consumers. ## Asynchronous texture ownership

`sunTexture.worker.ts` reads a local File and decodes the selected raster off the main thread, then transfers decoded mip buffers to the caller. The input file limit remains 64 MiB. `LocalSunTexture` owns a single GPU texture for eventual sharing between both sun draws. A successful replacement creates the new texture before replacing the current reference and releasing the old one. Decode/startup/transport failures preserve the previous raster. A newer request, clear or disposal terminates pending work and settles its promise as canceled; callbacks from superseded workers cannot commit. Completed workers terminate as well. Disposal releases the current texture once and prevents future loads.

Consumers borrow the owner's current raster for the current frame; they must neither dispose it nor keep a replaced reference. The renderer still needs to connect this contract to its two corona draws and a local file picker. The owner preserves native sampler/mip metadata and does not decide sprite shape, projection scale, display-space blending or texture alpha policy.

Verification: 262 unit tests across 53 files, build and the targeted real-worker GPU browser test passed. Fake-worker unit cases cover atomic replacement, failure retention, supersession, clear/disposal, stale callbacks, startup/transport errors and single disposal. The browser fixture loads synthetic red/blue coronastar dictionaries through the actual worker, verifies both rendered colors, retains red pixels after a bad replacement and checks that replacement retains one GPU texture while clear releases it to zero. The worker is currently reached through the diagnostic fixture, not the production game entry point; production bundling/UI integration and full gameplay tests were therefore not claimed or rerun for this stage.

## Raster orientation and measured extent checks

The original textured quad used PlaneGeometry UVs directly, placing the first decoded raster row at the bottom of the screen. The vertex shader now reverses V so that row is displayed at the top. Supporting source evidence comes from `CSprite::Set4Vertices2D` and `RenderOneXLUSprite2D` in the pinned Sprite.cpp: V=0 accompanies the smaller screen Y coordinate. The [CRect constructor](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Core/Rect.h) takes `(left, bottom, right, top)` despite its misleading field names, so the call's center-minus-size Y becomes the V=0 edge. This is evidence from the related 2D helper, not a recovered implementation of the unreversed rotated-aspect sun routine.

A four-color 2×2 diagnostic raster now verifies all four screen quadrants, avoiding the blind spot of a single-color or radially symmetric fixture. The GPU test scans the complete framebuffer to measure drawn bounds and center in landscape/portrait viewports and at two depths. These measurements verify the existing provisional half-extent calculation within one raster pixel, not its retail accuracy. All three targeted sun GPU/browser checks and build passed. Unit, full-gameplay and production runs were not repeated for this localized shader-coordinate change. Native rotated-sprite orientation, aspect correction, precise extents and retail captures remain separate verification requirements.

## Camera FOV and viewport conversion

The pinned [CameraSize implementation](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/app/app_camera.cpp) distinguishes exclusive display modes from ordinary windows. In its non-exclusive branch, the supplied view window occupies the larger viewport axis and the smaller axis scales by the dimension ratio. The [SCREEN_VIEW_WINDOW macro](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/common.h) computes tan(FOV / 2). Thus a landscape source FOV is horizontal; it cannot be passed directly as Three.js's vertical camera angle. The exclusive branch instead uses the supplied aspect setting; [CDraw::CalculateAspectRatio](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Draw.cpp) selects 16:9, 5:4 or 4:3 from menu/camera state. Browser fullscreen is not evidence that the native exclusive branch applies.

The browser now explicitly follows the non-exclusive branch. `windowedCameraProjection` converts viewport dimensions and a source FOV into view-window axes and a Three.js vertical FOV. Resize preserves near/far clip values and clamps hidden-canvas dimensions to one before projection. A chosen source scalar of 70 degrees produces approximately 55.413 degrees vertical at 4:3, 42.996 at 16:9, and 70 in portrait. This replaces the previous fixed 55-degree vertical setting and intentionally tightens wide-screen framing.

The 70-degree gameplay baseline remains provisional: the pinned [CCam source](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Cam.cpp) assigns 70 in several explicit modes, but its follow-ped routines are unreversed and do not establish a universal constant. Vehicle speed changes, camera transitions, zoom, aspect settings and PS2 presentation require separate reconstruction. The windowed PC policy is an explicit browser adaptation, not an assertion of PS2 or exclusive-mode parity.

`GameRenderer` now passes its source scalar through `WorldLighting` into `TexturedSun`; sprite scale no longer hides a separate hardcoded FOV. The sun raster GPU fixture also uses the converted camera and checks 35-, 70- and 100-degree scalar cases. Sprite size still follows the provisional half-extent interpretation described above. Sharing the correct kind of FOV does not verify the unreversed rotated-aspect routine, weather stretching or retail pixels.

Projection tests check actual Three.js frustum edges, equal pixel lengths, landscape/portrait/square cases, preserved clip planes and rejection before mutation. GPU checks measure sun raster bounds under multiple source FOVs as well as viewport shapes/depths. ## Sun visibility and building ambient coupling

The pinned [CCoronas::Update](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/Coronas.cpp) restores `LightsMult` by timestep × 0.03, capped at 1, before updating corona slots. [CRegisteredCorona::Update](https://github.com/gta-reversed/gta-reversed/blob/0076f9017b4aeef7433957ac2bd8b6988e9df166/source/game_sa/RegisteredCorona.cpp) subtracts timestep × 0.06, floored at 0.6, for ID 2 in its unobstructed, on-screen branch. This uses the preceding render's offscreen flag. The subtraction precedes slot expiry and does not require current registration or nonzero faded intensity. Thus the final clear on-screen fade update can still lower the multiplier. The core never lowers it. The header annotates the initial global as 1.0.

`SunCoronas` now owns that scalar per session. It shares the fade controller's capped native timestep conversion and zero-duration browser pause policy. Recovery always precedes any eligible ID-2 attenuation, including camera-look brightness changes. Blocked/offscreen or absent corona states recover without attenuation. JavaScript number arithmetic remains an approximation of native float arithmetic.

The pinned [SkyGFX building pipeline](https://github.com/aap/skygfx/blob/926616a3f31deaf0d300b3752383314db28994f0/src/buildingPipe.cpp) supplies building ambient as timecycle ambient multiplied by `CCoronas::LightsMult`. The browser applies that multiplier to its shared imported-building ambient uniform after choosing local timecycle or authored fallback ambient. It does not change baked vertex color, wet alpha, diffuse coefficients or the procedural environment's unrelated lighting. The scene time update now runs in `beforeRender`, after the lighting controller updates the sun, so the current multiplier reaches the current draw even within the same hour. The scene API defaults the multiplier to 1 for standalone consumers and rejects invalid values before changing uniforms; it does not mutate the supplied ambient tuple.

Cloud obstruction, interior eligibility, other native lighting consumers, native scheduling/float precision and original captures remain unresolved. This implements one evidenced building-pipeline consumer; it is not a claim that the whole world's lighting matches the original engine.
